# KPI по результату и мотивация

Реализация согласованных макетов Aura Estate: [Figma](https://www.figma.com/design/mnhQ7SfxnXl8y6pncY6dcZ?node-id=42-5641). Отдельна от прежнего взвешенного KPI активности. Фронтенд использует API-результат, включая верхнюю плашку.

## Правила

- Продажи и аренда считаются отдельно. Цель: количество, сумма либо количество ИЛИ сумма. Для ИЛИ прогресс равен большему из двух процентов; они не складываются. Любая полностью выполненная ветка достаточна.
- Сумма — цена проданного объекта или стоимость аренды. Комиссия и залог не входят. Аренда выбирается в версии цели: `monthly_rent` или `contract_total`.
- Валюта TJS/USD. `deal_fx_rate` хранит TJS за 1 USD на дату сделки. Текущий курс не применяется к прошлым сделкам. Недостающая сумма/основа/курс помечается как неполная информация; известная часть — нижняя граница.
- Полный зачёт основному продавцу: sale_agent_id, затем sale_user_id, agent_id, created_by. Продажа собственником без агентства не считается. Повторное открытие объекта добавляет отменяющую ревизию, повтор того же события не дублирует зачёт.
- Новый журнал фактов хранит UTC и подразделение на момент закрытия. Старые записи читаются в APP_TIMEZONE; календарный период всегда Asia/Dushanbe. Исторические сделки без журнала отмечаются `legacy_scope`: их группа берётся из текущей карточки сотрудника. Неизвестные сведения не восстанавливаются предположениями.
- Личная цель заменяет шаблон группы для месяца и вида сделки. Версии публикуются с expected_version. Текущий опубликованный план неизменяем; новые редакции предназначены для будущего месяца.
- Закрытие завершённого месяца сохраняет снимок. Изменение снимка требует предварительного сравнения, токена актуальности, причины и права корректировки. Все версии сохраняются.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/kpi/results | month=YYYY-MM; необязательные user_id, branch_id, branch_group_id |
| GET / POST | /api/kpi/results/goals | Чтение версий / публикация цели |
| POST | /api/kpi/results/close | Фиксация завершённого месяца сотрудника |
| POST | /api/kpi/results/adjust | preview=true; затем preview_token и reason |
| GET | /api/kpi/results/period-history | История корректировок |
| GET / POST / PATCH | /api/motivation/rules[/{id}] | Программы; can_manage отражает доступ к каждой программе |
| POST | /api/motivation/recalculate | Предпросмотр изменений, затем применение preview_token |
| POST | /api/motivation/achievements/{id}/transition | verify, approve, return, issue, resolve_review |
| GET | /api/motivation/achievements/{id}/history | Аудит решений |

Программы можно связать с личной целью KPI либо задать независимое условие. Область — группа, филиал или компания. Денежные суммы задаёт уполномоченный сотрудник; демонстрационные премии из макетов автоматически не создаются. Существующие программы Ташкент/Умра/общая цель остаются в базе.

## Роли и выдача

РОП ограничен назначенными группами. Директор — своим филиалом. Права управления условиями, проверки, согласования и выдачи разделены. Собственные назначения и изменения проверяются на сервере под блокировками; компания недоступна группе через расширенное разрешение scope.all.

Путь награды: выполнено → проверено РОП → согласовано после окончания периода → фактически выдано. Для выдачи нужны дата, способ, подтверждающий документ и UUID команды. Повтор той же команды безопасен; иная повторная выдача запрещена. Уже выданная награда не отзывается автоматически при коррекции сделки: появляется ручная проверка. Её завершение сохраняет обоснование и запись о выдаче; денежных операций система не проводит.

`motivation:refresh` проверяет активные программы каждые пять минут через существующий Laravel scheduler. Он фиксирует достижения и изменения, но не согласовывает и не выдаёт награды.

## Выпуск и совместимость

Нужны три миграции 2026_11_05_140000, 150000, 160000. API и миграции должны быть доступны до включения нового фронтенда. Старые отчёты и пути API сохраняются; старый экран активности перенесён на /profile/kpi/activity. В старых отчётах продажи читают тот же журнал без повторного зачёта.

Развёртывание этой задачей не выполняется. Перед отдельным выпуском проверить миграции на копии рабочей БД и действующий scheduler. Для отката приложения сохранять добавленную схему и аудит. Down миграции программ остановится до удаления данных, если независимые программы уже нарушают старый уникальный ключ.

## Проверка

Серверные тесты покрывают OR, границы округления и месяца в UTC/Душанбе, валюту и обе основы аренды, версии, повторные события/выдачу, закрытие/коррекцию, скрытые филиалы, назначенные группы РОП и выдачу по ролям. Расширенный набор включает прежние KPI, атрибуцию и модерацию сделок. SQLite проверяет бизнес-логику; реальные блокировки MySQL требуют проверки на окружении выпуска.

Браузерные тесты фронтенда используют синтетические ответы API и отдельные проверки серверного контракта; они не выполняют операций в рабочей системе. Проверяются 360/390/1600 px, диалоги, сохранение формы при ошибке, доступ только на чтение, смена области/отзыв прав, экспорт и тёмная тема. Это не исследование с реальными пользователями и не проверка на физических телефонах.
