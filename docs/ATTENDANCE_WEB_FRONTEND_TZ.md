# ТЗ: web-интерфейс посещаемости Aura

## 1. Цель

Разработать web-раздел посещаемости сотрудников Aura на основе данных терминалов ZKTeco.

Интерфейс должен позволять:

- просматривать посещаемость пользователей по дням;
- видеть время первого прихода и последнего ухода;
- быстро находить опоздавших, отсутствующих и пользователей с незавершённым днём;
- анализировать посещаемость по филиалам;
- открывать все проходы конкретного пользователя за день;
- оставлять официальный комментарий HR к опозданию;
- сопоставлять ZKTeco User ID с активным пользователем Aura;
- видеть несопоставленные события и результат их повторной обработки.

Все даты и время в интерфейсе отображаются в `Asia/Dushanbe`.

## 2. Область первой версии

Первая версия включает три вкладки:

1. `Журнал` — основная таблица «пользователи × дни».
2. `Синхронизация` — связи ZKTeco User ID с пользователями Aura и несопоставленные события.
3. `Терминалы` — состояние устройств; доступна только административным ролям.

Не входят в первую версию:

- загрузка лиц, фотографий или RFID-карт через Aura;
- изменение времени исходного прохода;
- расчёт заработной платы;
- автоматическое признание опоздания уважительным;
- достоверный статус «сейчас в офисе»;
- полноценная двусторонняя синхронизация справочника пользователей с терминалом.

Комментарий HR не изменяет исходный проход, число минут опоздания или рассчитанный статус. Он является пояснением к зафиксированному факту.

## 3. RBAC

Под доступом `РОП+` в этом ТЗ понимаются:

- `rop`;
- `branch_director`;
- `admin`;
- `superadmin`;
- `owner`.

HR добавляется к этому списку как отдельная функциональная роль. Итоговый доступ к общей таблице имеют:

```text
rop, branch_director, hr, admin, superadmin, owner
```

| Действие | ROP | Директор филиала | HR | Admin / Superadmin / Owner |
|---|---:|---:|---:|---:|
| Просмотр общей таблицы | Свой филиал | Свой филиал | Все филиалы | Все филиалы |
| Просмотр деталей дня | Свой филиал | Свой филиал | Все филиалы | Все филиалы |
| Просмотр филиальной аналитики | Свой филиал | Свой филиал | Все филиалы | Все филиалы |
| Добавление/редактирование HR-комментария | Нет | Нет | Да | Да |
| Сопоставление ZKTeco ID | Нет | Нет | Да | Да |
| Просмотр несопоставленных событий | Нет | Нет | Да | Да |
| Управление терминалами | Нет | Нет | Только просмотр | Да |

Правила безопасности применяются на backend. Скрытие кнопки на frontend не считается проверкой доступа.

Остальные активные пользователи не видят общую таблицу, но сохраняют доступ к собственному разделу `/attendance/me` согласно основному ТЗ backend.

## 4. Навигация

Пункт меню:

```text
Сотрудники → Посещаемость
```

Маршрут web-приложения:

```text
/attendance
```

Frontend получает разрешения от backend и показывает только доступные вкладки и действия:

```json
{
  "can_view_attendance_table": true,
  "can_view_all_branches": true,
  "can_comment_late_day": true,
  "can_manage_mappings": true,
  "can_manage_devices": false
}
```

Запрещённый прямой переход возвращает экран `Нет доступа`, а не пустую таблицу.

## 5. Вкладка «Журнал»

### 5.1. Верхняя панель

В верхней части страницы располагаются:

- заголовок `Посещаемость`;
- переключатель режима `Сотрудники / Филиалы`;
- период `Неделя / Месяц`;
- выбор даты или месяца;
- время последнего обновления;
- кнопка `Обновить`;
- кнопка `Экспорт CSV`;
- кнопка `Фильтры` на узких экранах.

Период по умолчанию — текущий месяц. Будущие дни отображаются пустыми и не считаются отсутствием.

Максимальный диапазон одного запроса — 31 день. Более длинный период должен формироваться отдельным отчётом, а не расширением интерактивной таблицы.

### 5.2. Фильтры

Фильтры располагаются одной компактной строкой:

- филиал;
- группа филиала;
- роль;
- пользователь;
- статус дня: `Все`, `Вовремя`, `Опоздал`, `Отсутствует`, `Неполный день`;
- способ идентификации: лицо, карта, отпечаток, пароль, неизвестно;
- терминал;
- переключатель `Только с комментариями HR`;
- поиск по имени или Aura User ID.

Для ROP и директора филиал принудительно задаётся backend и не может быть изменён query-параметром.

Состояние фильтров сохраняется в URL. После возврата на страницу пользователь видит тот же период и фильтры.

### 5.3. Сводные показатели

Над таблицей показываются компактные показатели за выбранный период:

- активных пользователей в области доступа;
- пришли сегодня;
- опоздали сегодня;
- отсутствуют сегодня;
- неполных дней;
- среднее опоздание в минутах.

Карточки являются быстрыми фильтрами. Например, нажатие на `Опоздали сегодня` показывает только опоздавших за текущую дату.

### 5.4. Матрица «пользователи × дни»

Строка соответствует пользователю, колонка — календарному дню.

Закреплённые слева колонки:

| Колонка | Содержимое |
|---|---|
| Пользователь | Аватар, имя, Aura User ID |
| Роль | Локализованное название роли |
| Филиал / группа | Название филиала и группы |
| Итого | Дни вовремя, опоздания, отсутствия, среднее опоздание |

Дневные колонки имеют заголовок из числа и короткого дня недели. Текущий день визуально выделяется. Выходные дни имеют нейтральный фон.

Содержимое ячейки рабочего дня:

```text
09:07 → 18:14
Опоздание +7 мин
```

Состояния ячейки:

| Состояние | Отображение |
|---|---|
| `present` | Приход и уход, зелёный индикатор `Вовремя` |
| `late` | Приход и уход, оранжевый/красный индикатор `+N мин` |
| `incomplete` | Единственный проход и индикатор `Нет ухода` |
| `absent` | Индикатор `Отсутствовал` |
| Нерабочий день | `Выходной`, нейтральный фон |
| Будущий день | Пустая ячейка |
| Нет рассчитанных данных | `—`, без утверждения об отсутствии |

Цвет не используется как единственный носитель смысла: каждая ячейка содержит текст или иконку с доступным названием.

Если есть HR-комментарий, в ячейке отображается иконка комментария. Полный текст открывается по нажатию.

Строки группируются по филиалам с раскрываемым заголовком филиала. Внутри филиала доступна дополнительная группировка по команде.

Таблица должна поддерживать:

- закреплённую шапку;
- закреплённые колонки пользователя;
- горизонтальную прокрутку только области дней;
- серверную пагинацию пользователей по 50 строк;
- сортировку по имени, количеству опозданий и среднему опозданию;
- раскрытие строки без потери позиции прокрутки;
- skeleton во время первой загрузки;
- сохранение старых данных во время фонового обновления.

Frontend не выполняет отдельный HTTP-запрос для каждой ячейки.

## 6. Режим «Филиалы»

В режиме `Филиалы` строка соответствует филиалу, колонка — дню.

Ячейка филиала показывает:

```text
Пришли 24 / 30
Опоздали 5
Отсутствуют 4
Неполный день 2
```

Показатель посещаемости филиала:

```text
attendance_pct = checked_in_count / scheduled_users_count × 100
```

Где `checked_in_count` включает `present`, `late` и `incomplete`, а знаменатель включает только активных пользователей, для которых этот день является рабочим.

Клик по ячейке переводит в режим `Сотрудники` с уже установленными фильтрами филиала и даты.

Для ROP и директора отображается только их филиал. HR и административные роли могут сравнивать все филиалы.

## 7. Детали дня пользователя

Нажатие на дневную ячейку открывает боковую панель без ухода со страницы.

Панель содержит:

- имя, роль, филиал и группу;
- рабочую дату и график на этот день;
- первый приход;
- последний уход;
- отработанные минуты;
- минуты опоздания;
- итоговый статус;
- список всех проходов по времени;
- терминал каждого прохода;
- способ идентификации;
- отметку о семантическом дубле, если она нужна администратору;
- HR-комментарий;
- автора и время последнего изменения комментария.

Сырые payload, IP-адреса и технические ошибки не показываются ROP или директору. Они остаются в административном интерфейсе.

## 8. Комментарий HR к опозданию

Кнопка `Добавить комментарий` отображается, если:

- день имеет `late_minutes > 0`;
- пользователь имеет разрешение `can_comment_late_day`.

Форма содержит одно поле:

```text
Комментарий — обязательный, 1–2000 символов
```

Примеры комментариев:

- `Предупредил о визите к врачу.`
- `Опоздание подтверждено руководителем.`

Правила:

- в первой версии у пользователя может быть один официальный HR-комментарий на день;
- HR и административные роли могут создать, изменить или удалить комментарий;
- ROP и директор видят комментарий, но не меняют его;
- текст отображается как обычный текст, HTML не исполняется;
- каждое создание, изменение и удаление записывается в аудит;
- комментарий не меняет `late_minutes`, `status` или исходные события;
- при параллельном изменении frontend должен показать конфликт и предложить обновить данные.

После успешного сохранения обновляются только открытая панель и соответствующая ячейка, без полной перезагрузки матрицы.

## 9. Вкладка «Синхронизация»

### 9.1. Принцип синхронизации

В первой версии терминал присылает в ATTLOG только `Device User ID`, время, статус и способ идентификации. Имя пользователя, лицо и RFID-шаблон не передаются.

Поэтому применяется явная связь:

```text
Терминал + ZKTeco User ID → Aura User ID
```

Рекомендуемое правило регистрации:

```text
ZKTeco User ID = users.id в Aura
```

Совпадение идентификаторов упрощает работу, но отдельная запись сопоставления создаётся всегда.

### 9.2. Несопоставленные пользователи терминала

Верхний блок показывает сгруппированные несопоставленные события:

| Поле | Описание |
|---|---|
| Терминал | Название и серийный номер |
| ZKTeco User ID | ID из ATTLOG |
| Первый проход | Самое раннее событие |
| Последний проход | Самое позднее событие |
| Событий | Количество ожидающих событий |
| Способ | Лицо, карта и т. п. |
| Действие | `Связать` |

По нажатию `Связать` HR выбирает активного пользователя Aura через поиск по имени, телефону или Aura User ID.

Если числовой ZKTeco User ID совпадает с Aura User ID активного пользователя, frontend показывает этого пользователя как рекомендуемый вариант. Связь всё равно создаётся только после явного подтверждения HR; автоматическая привязка по совпадению номера запрещена.

Перед сохранением frontend показывает подтверждение:

```text
ZKTeco User ID 1 на терминале «Главный вход»
будет связан с Aura User ID 1 — Admin.
Будут повторно обработаны 2 события.
```

После сохранения backend автоматически повторно обрабатывает все ожидающие события этой пары. Frontend показывает результат:

```text
Обработано: 2
Осталось несопоставленных: 0
Уже обработано: 0
```

### 9.3. Действующие сопоставления

Нижний блок показывает:

- терминал;
- ZKTeco User ID;
- пользователь Aura;
- роль;
- филиал;
- состояние связи;
- кто и когда создал связь;
- количество обработанных событий.

Доступные действия:

- отключить связь для будущих событий;
- включить ранее отключённую связь;
- открыть посещаемость пользователя.

Если по связи уже существуют нормализованные события, переназначение на другого пользователя запрещается. Интерфейс объясняет причину и предлагает создать новый ZKTeco User ID на терминале. Это защищает историю посещаемости.

HR редактирует здесь только связь с терминалом. Имя, телефон, роль, филиал и состояние пользователя меняются в существующем разделе управления пользователями Aura.

## 10. Вкладка «Терминалы»

Карточка терминала показывает:

- название;
- серийный номер;
- филиал;
- состояние `online/offline`;
- последнее соединение;
- последнее событие;
- расхождение часов;
- количество активных сопоставлений;
- последнюю ошибку.

HR имеет read-only доступ. Создание, изменение филиала, communication key и отключение терминала доступны только `admin`, `superadmin`, `owner`.

## 11. Необходимые backend-контракты

Текущие API событий и дневных сводок сохраняются. Для эффективной web-матрицы необходимо добавить агрегированный endpoint.

### 11.1. Матрица

```http
GET /api/attendance/matrix
```

Параметры:

```text
date_from, date_to, view=users|branches,
branch_id, branch_group_id, role, user_id,
status, verification_method, device_id,
has_comment, search, sort, page, per_page
```

Упрощённый ответ режима пользователей:

```json
{
  "data": [
    {
      "user": {
        "id": 1,
        "name": "Admin",
        "role": "admin",
        "branch_id": 2,
        "branch_name": "Филиал 102",
        "branch_group_id": null,
        "branch_group_name": null
      },
      "totals": {
        "present": 12,
        "late": 3,
        "absent": 1,
        "incomplete": 1,
        "average_late_minutes": 8
      },
      "days": {
        "2026-08-16": {
          "status": "present",
          "is_working_day": false,
          "first_in_at": "2026-08-16T14:50:49Z",
          "last_out_at": "2026-08-16T15:03:09Z",
          "worked_minutes": 12,
          "late_minutes": 0,
          "events_count": 2,
          "verification_methods": ["face"],
          "has_comment": false,
          "comment_preview": null
        }
      }
    }
  ],
  "meta": {
    "timezone": "Asia/Dushanbe",
    "date_from": "2026-08-01",
    "date_to": "2026-08-31",
    "permissions": {
      "can_comment_late_day": true,
      "can_manage_mappings": true,
      "can_manage_devices": false
    },
    "summary": {},
    "pagination": {}
  }
}
```

Endpoint возвращает одну строку на пользователя, а не одну запись на пользователя и день. Это исключает N+1-запросы frontend и разрыв строки между страницами.

### 11.2. Детали дня

```http
GET /api/attendance/users/{user}/days/{date}
```

Ответ содержит дневную сводку, график, комментарий и полный список нормализованных проходов в порядке времени.

### 11.3. HR-комментарий

```http
PUT    /api/attendance/users/{user}/days/{date}/comment
DELETE /api/attendance/users/{user}/days/{date}/comment
```

Payload:

```json
{
  "comment": "Предупредил о визите к врачу.",
  "version": 3
}
```

Для хранения создаётся таблица `attendance_daily_comments`:

- `id`;
- `user_id`;
- `work_date`;
- `comment`;
- `created_by`;
- `updated_by`;
- `version` для optimistic locking;
- `created_at`;
- `updated_at`;
- unique (`user_id`, `work_date`).

Права изменения: `hr`, `admin`, `superadmin`, `owner`. Все изменения записываются в `attendance_audit_logs`.

### 11.4. Сопоставления

Используются существующие endpoints:

```http
GET /api/attendance/device-users
PUT /api/attendance/device-users
GET /api/attendance/unmapped-events
```

Backend необходимо разрешить управление сопоставлениями ролям:

```text
hr, admin, superadmin, owner
```

Управление самими терминалами остаётся только для:

```text
admin, superadmin, owner
```

Для вкладки синхронизации `GET /api/attendance/unmapped-events` должен поддерживать `grouped=true`, группируя по `device_id + device_user_id` и возвращая количество, первое и последнее событие.

### 11.5. Экспорт

```http
GET /api/attendance/export
```

Экспорт применяет те же фильтры и RBAC, что матрица. CSV содержит UTF-8 BOM и безопасные для Excel текстовые значения.

## 12. Состояния интерфейса

Необходимо реализовать:

- skeleton первой загрузки;
- пустое состояние `За выбранный период данных нет`;
- отдельное состояние `Нет пользователей по выбранным фильтрам`;
- ошибка сети с кнопкой `Повторить`;
- ошибка доступа без повторной отправки запроса;
- частичное обновление без очистки таблицы;
- предупреждение о давно не обновлявшемся терминале;
- подтверждение перед изменением сопоставления;
- понятное сообщение при конфликте версии комментария.

## 13. Адаптивность и доступность

- основной сценарий оптимизируется для desktop от 1280 px;
- на планшете закрепляются имя пользователя и выбранный день, остальные дни прокручиваются горизонтально;
- на телефоне матрица заменяется списком пользователей с раскрываемыми днями;
- все действия доступны с клавиатуры;
- интерактивная ячейка имеет видимый focus-state;
- tooltip не является единственным способом получить информацию;
- цветовые статусы сопровождаются текстом;
- контраст соответствует WCAG AA;
- время отображается в формате `HH:mm`, дата — в локальном формате интерфейса.

## 14. Производительность

- один запрос матрицы на изменение фильтров;
- debounce поиска 300–400 мс;
- отмена устаревшего запроса при смене периода;
- серверная пагинация по пользователям;
- кэширование справочников филиалов, групп, ролей и терминалов;
- отсутствие запросов на каждую ячейку;
- виртуализация строк при отображении более 50 пользователей;
- фоновое обновление не чаще одного раза в 60 секунд;
- ручная кнопка `Обновить` всегда доступна.

## 15. Аналитика действий

Рекомендуемые frontend-события без персональных данных:

- `attendance_table_opened`;
- `attendance_filter_applied`;
- `attendance_day_opened`;
- `attendance_comment_saved`;
- `attendance_mapping_started`;
- `attendance_mapping_completed`;
- `attendance_export_started`.

В аналитику нельзя передавать текст HR-комментария, имя, телефон, Device User ID или raw ATTLOG.

## 16. Проверки frontend

### Unit/component

- отображение всех статусов ячейки;
- расчёт текста `+N мин`;
- выходной и будущий день не выглядят отсутствием;
- комментарий экранируется;
- разрешения скрывают недоступные действия;
- филиальные агрегаты отображаются без локального пересчёта backend-данных.

### Integration

- фильтры синхронизируются с URL;
- ROP не может запросить другой филиал;
- HR может создать, изменить и удалить комментарий;
- ROP видит комментарий без кнопки редактирования;
- HR связывает ZKTeco ID с пользователем и видит результат reprocess;
- конфликт сопоставления отображает объяснение;
- открытие ячейки загружает детали одного дня;
- экспорт получает те же фильтры.

### E2E

1. HR открывает текущий месяц и филиал.
2. Находит опоздавшего пользователя по фильтру.
3. Открывает день и сохраняет комментарий.
4. ROP этого филиала видит комментарий, но не может его изменить.
5. HR открывает несопоставленный ZKTeco ID и связывает его с активным пользователем.
6. События исчезают из несопоставленных и появляются в матрице.
7. ROP другого филиала не видит пользователя даже при ручной подмене query-параметров.

## 17. Критерии приёмки

- общая таблица доступна только разрешённым ролям;
- backend всегда ограничивает ROP и директора их филиалом;
- матрица корректно показывает пользователей и дни без N+1-запросов;
- приход, уход и минуты опоздания отображаются в `Asia/Dushanbe`;
- выходной, будущий день и отсутствие данных визуально различаются;
- опоздавших можно найти одним фильтром или нажатием на сводный показатель;
- HR-комментарий сохраняется, отображается ROP и записывается в аудит;
- комментарий не изменяет рассчитанную посещаемость;
- филиальная таблица показывает одинаковые с backend итоги;
- HR может связать любой ZKTeco User ID с любым активным пользователем Aura независимо от роли;
- после сопоставления ожидающие события автоматически обрабатываются;
- историю обработанных посещений нельзя незаметно переназначить другому пользователю;
- интерфейс не получает и не хранит биометрические данные;
- CSV открывается в Excel с корректной кириллицей;
- основные сценарии покрыты unit, integration и E2E-тестами.
