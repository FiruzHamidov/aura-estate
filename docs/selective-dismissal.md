# Выборочная передача записей при увольнении

В списке пользователей и карточке сотрудника действие увольнения открывает план передачи. Для каждого раздела (объявления, клиенты и остальные активные CRM-записи) можно выбрать одного или нескольких получателей, распределить записи поровну внутри выбранного набора, затем изменить получателя отдельной записи. Распределение учитывает допустимых получателей каждой записи, а не текущую нагрузку сотрудников. Неназначенные записи блокируют отправку.

## API

- `GET /api/user/{user}/dismissal-preview`: возвращает `revision`, `records` с `type`, `id`, `title`, `branch_id`, `branch_group_id`, `eligible_user_ids`, а также `recipients`.
- `DELETE /api/user/{user}` с телом:

```json
{
  "transfer_plan": {
    "revision": "64-символьный хеш из preview",
    "reason": "Увольнение сотрудника",
    "records": [
      {"type": "properties", "id": 123, "responsible_user_id": 45},
      {"type": "clients", "id": 456, "responsible_user_id": 67}
    ]
  }
}
```

В плане должны присутствовать все и только записи из preview, без повторений. При отсутствии записей передаётся пустой массив. `reason`: 5–2000 символов. Ответ содержит `transferred_counts` по типам и `clients_transferred_count`; прежние поля ответа сохранены.

## Ограничения и целостность

Права увольнения проверяются и при preview, и после блокировки сотрудника. Получатель — активный агент или МОП, не увольняемый сотрудник, в той же группе и филиале, что и запись. Для записей без группы доступны сотрудники без группы соответствующего филиала. Смена группы выполняется отдельным существующим процессом перевода.

План применяется в одной транзакции с отзывом доступа. Изменение состава или содержимого активных записей после preview возвращает 409 `DISMISSAL_VERSION_CONFLICT`. Неполный план, повторения и недопустимые получатели возвращают 422. Любая ошибка откатывает назначения и аудит, сотрудник остаётся активным. Фронтенд обновляет preview и требует повторного выбора.

Закрытая история и группы не меняются. У клиента меняется ответственный также в потребностях. У объявления сохраняется автор создания; новый ответственный задаётся явно. Соучастник не получает приоритет над планом, совпадение с новым ответственным удаляется. Версия модерации увеличивается, передача записывается в `group_access_audit_logs`. Другие активные записи сотрудника также требуют назначения, чтобы не оставлять их без действующего ответственного.

Старые параметры `distribute_to_agents` / `agent_id` остаются совместимыми со старым API. Новый веб-интерфейс всегда отправляет проверенный план. Новых миграций нет; используется существующая схема группового доступа.
