# Результаты показов: первая версия

Результат хранится в существующем показе. Основной агент и один соучастник могут заполнить его позже, если у них есть `bookings.update.own`. Пользователь с `bookings.update.all` может изменить доступный ему показ. Ограничения филиала и назначенных РОПу групп сохраняются.

Все поля результата необязательные. Истечение времени показа не меняет статус. Отчёты и KPI продолжают считать количество созданных показов по прежним правилам авторства, независимо от статуса и реакции клиента. Соучастие не добавляет второй показ в отчёт.

## Получение

`GET /api/bookings/{id}` и строки `GET /api/bookings` содержат:

- `status`: `pending` (запланирован), `confirmed`, `completed` (проведён), `not_held`, `cancelled`.
- `outcome`: `interested`, `thinking`, `not_suitable`, `undecided` или `null`.
- `result_reason`: `price`, `location`, `condition`, `layout`, `client_no_show`, `owner_unavailable`, `property_unavailable`, `other` или `null`.
- `result_note`, `result_recorded_at`, `result_recorded_by`, `result_version`.
- `needs_result`: вычисляется для `pending` / `confirmed`, когда `end_time` уже прошло.
- `can_view_result`, `can_record_result`, `can_schedule_follow_up`: возможности текущего пользователя.
- `follow_up`: связанная задача `{id, due_at, status, assignee_id}`, если она есть и доступна.

Пользователям без доступа сотрудников внутренние поля результата не возвращаются. История им недоступна.

`GET /api/bookings?needs_result=1` возвращает только прошедшие по времени показы без результата. Фильтр необязателен и применяется только при явной передаче. Список поддерживает обычные фильтры и пагинацию. Для карточки клиента используется `crm_client_id`, без `needs_result`, чтобы показывать все его доступные показы.

## Сохранение

`PATCH /api/bookings/{id}/result`:

```json
{
  "version": 0,
  "status": "completed",
  "outcome": "thinking",
  "result_note": "Клиент обсудит с семьёй",
  "next_contact_at": "2026-11-20T10:00:00+05:00"
}
```

`version` — техническая версия из прочитанной карточки; вводить её пользователю не нужно. Все остальные поля можно пропустить. Запрос только с актуальной версией ничего не меняет. `null` очищает реакцию, причину, заметку или следующий контакт; `status: null` сохраняет текущий статус. Заметка ограничена 5000 символами.

Передача реакции без статуса отмечает показ проведённым. Если явно указан другой статус, реакция очищается. При смене статуса прежняя причина очищается, если новая причина не передана.

Только явно переданная дата контакта создаёт задачу `CALL` основному агенту. Обновление даты меняет ту же активную задачу; `null` отменяет её. После завершения/отмены задачи новая дата создаёт новую задачу. Без даты задача не создаётся и не меняется. Нужны права на задачи и действующий основной агент в группе показа. При недоступности этой возможности результат можно сохранить, исключив `next_contact_at` из запроса.

Ответ — свежая карточка. При изменившейся версии сервер отвечает `409 BOOKING_RESULT_CHANGED`, сохраняя чужое изменение. Клиент сохраняет черновик формы и предлагает явно перечитать запись; автоматическая повторная запись запрещена логикой клиента. Неверные значения дают `422`, без частичного сохранения результата или задачи.

## Перенос и история

`PATCH /api/bookings/{id}/reschedule` принимает `version`, `start_time`, `end_time`. При переносе нужны обе даты, окончание позже начала и начало не в прошлом по серверному времени. Даты с часовым поясом нормализуются в UTC, без пояса трактуются как время Душанбе. Запрос без новых дат ничего не меняет.

Перенос сохраняет ID и автора, устанавливает `pending`, очищает текущий результат и увеличивает версию. Старый результат остаётся в истории. Связанная задача контакта сохраняет свою дату; интерфейс сообщает об этом. Изменение расписания через прежний `PATCH /api/bookings/{id}` также записывает перенос и сбрасывает текущий результат.

`GET /api/bookings/{id}/history?page=1` возвращает по 20 событий `booking_result_updated` / `booking_rescheduled` с автором, временем, прежними и новыми значениями. Новые события идут первыми.

## Совместимость

Миграция `2026_11_18_150000_add_booking_results.php` расширяет статус до строки и добавляет nullable-поля результата. Старые показы сохраняют прежние статусы; они не становятся проведёнными автоматически. Нужна ранее добавленная миграция соучастника. До применения миграции API чтения возвращает `can_record_result: false`.

Интерфейс результатов подключён к веб-календарю, карточке клиента и просмотру показа в CRM. Мобильные клиенты продолжают читать строковый статус; отдельная форма результата в нативных приложениях в эту версию не входит.
