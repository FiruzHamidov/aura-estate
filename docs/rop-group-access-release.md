# Подготовка и выпуск групповой политики РОП

Выпуск backend и совместимого aura-front выполняется вместе. Запрещён аварийный возврат РОП к филиальной видимости. Этот порядок не является разрешением на production-деплой.

1. Сделать резервную копию БД и приватных медиа. На период итоговой подготовки остановить изменения организационной структуры, назначений и бизнес-записей; остановить фоновые обработчики, которые их изменяют. Это исключает устаревание инвентаризации между проверкой и включением приложения.
2. Применить миграции. Новые поля группы/исторического контекста не заполнять текущей группой сотрудника задним числом. Обратные миграции новой классификации её не удаляют.
3. Выполнить `php artisan rop-groups:prepare` и сохранить JSON в закрытом хранилище выпуска. Проверить `rop_assignments`, `rops_without_groups`, `issues`, `cross_group_links`, неизвестные исторические группы, роли и графики. Межгрупповая ссылка сама по себе не переносит карточку.
4. Подготовить JSON назначений вида `[{"rop_id": 12, "branch_group_ids": [4, 5], "version": 0}]` с действительными ID и версиями. Проверить весь файл без записи: `php artisan rop-groups:prepare --assignments=/private/reviewed-assignments.json --actor=ADMIN_ID`. Повторные группы, чужие филиалы, устаревшая версия или неверная строка отклоняют весь импорт.
5. Применить подтверждённые назначения и однозначную классификацию: `php artisan rop-groups:prepare --apply --assignments=/private/reviewed-assignments.json --actor=ADMIN_ID`. Заполненные конфликты не перезаписываются. Сохранить отчёт и журнал аудита.
6. Выполнить `php artisan rop-groups:prepare --queue-review --check`. Ненулевой код завершения блокирует выпуск: активный РОП без назначения или ещё не применённая однозначная классификация требуют исправления. Неоднозначные записи допускаются только после явной публикации очереди. Повторный запуск без `--queue-review` при нерешённых конфликтах не проходит проверку. Команда не включает широкий доступ.
7. Проверить очередь через «Пользователи → Разбор групповой принадлежности» (`/admin/group-access-review`, API `GET /group-access/review`). Администратор видит все записи, директор — только однозначно определённый свой филиал, неопределённый филиал разбирает администратор. В очереди только идентификаторы и причины, без скопированных контактов. Исправлять исходные данные по подтверждённой принадлежности, через контролируемые операции передачи; не менять исторические факты по текущей группе. Затем повторить подготовку: исчезнувшие проблемы получают дату разрешения, история очереди сохраняется.
8. Приватизировать старые фотографии внешних заявок: сначала `php artisan rop-groups:privatize-request-photos`, затем после разбора отчёта `php artisan rop-groups:privatize-request-photos --apply`. Применить предоставленные правила веб-сервера для запрета старого публичного пути. Проверить авторизованное скачивание и отказ по старому URL.
9. Запустить локальные/стендовые проверки матрицы A/B, B/C, другого филиала, пустой области, отзыва доступа, версий, передачи, экспорта и приватных файлов. Backend: `php -d memory_limit=512M vendor/bin/phpunit`. Browser E2E находятся в aura-front/tests/e2e/rop-*.mjs; используют только изолированную фикстуру, не production-токены. Реальные внешние уведомления при проверке не отправлять.
10. Только после проверки совместимых версий возобновить приложение и фоновые процессы. После изменения назначений старые выгрузки/каналы привязаны к предыдущей версии и не должны использоваться повторно. При сбое закрыть затронутый модуль для РОП, сохранив назначения, группу и аудит.

Проверка `--check` подтверждает подготовку данных на момент сканирования; она не заменяет приёмку кода, маршрутного реестра и E2E. Рабочие РОП не получают назначения автоматически из своей рабочей группы.

## Отложенное назначение групп

Если владелец выпуска явно решил назначить группы после публикации, подготовку можно выполнить с `--allow-unassigned-rops`. Флаг разрешает только отсутствие назначений, не пропускает классификацию и очередь, не назначает группы автоматически и не открывает РОП рабочие данные. Пустая область остаётся закрытой до сохранения администратором групп в интерфейсе. Остальные проверки выпуска обязательны.
