ТЗ: ограничение доступа РОП по закреплённым группам

Дата: 08.09.2026. Статус: предлагаемая архитектура для реализации.

**1. Цель и основное правило**

РОП получает доступ к внутренним данным только закреплённых за ним групп своего филиала. Назначение в одну группу не открывает остальные группы филиала. Один РОП может курировать несколько групп; у одной группы может быть несколько РОП.

Пример: в филиале есть группы A, B и C. РОП-1 назначен в A и B, РОП-2 — в B и C. Оба видят B; РОП-1 не видит C, РОП-2 не видит A.

Формула разрешения:

`Доступ = разрешение роли на действие AND принадлежность записи разрешённой группе AND ограничения бизнес-процесса`.

Попадание записи в группу не даёт дополнительных прав на удаление, финансы, модерацию или изменение сотрудников. Существующие ограничения действий сохраняются; область данных для РОП сужается.

**2. Основание в текущем проекте**

В текущей рабочей копии backend уже существуют:

- `branch_groups` с привязкой к филиалу;
- `users.branch_group_id` — одна рабочая группа сотрудника;
- `clients.branch_group_id` и `properties.branch_group_id` — группа записи;
- `RbacBranchScope` и middleware `EnforceRopBranchScope`, которые ограничивают РОП филиалом;
- проверки, объединяющие `rop` и `branch_director`, в `ClientAccess`, `DealAccess`, `LeadAccess`, `BranchGroupController` и `PropertyModerationAccess`.

Поэтому добавления фильтра на фронтенде недостаточно. Нужно выделить групповую область РОП в серверной авторизации и применить её ко всем каналам получения и изменения данных.

**3. Вспомогательная таблица**

Создать `rop_branch_groups`. Таблица хранит действующие назначения РОП, а не копии сотрудников или бизнес-данных.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint, PK | Идентификатор назначения |
| `rop_id` | FK → users.id, NOT NULL | Пользователь с ролью `rop` |
| `branch_group_id` | FK → branch_groups.id, NOT NULL | Закреплённая группа |
| `assigned_by` | FK → users.id, nullable | Кто создал назначение; null допустим для системной миграции |
| `created_at`, `updated_at` | timestamp | Время создания и изменения |

Ограничения и индексы:

- UNIQUE (`rop_id`, `branch_group_id`) исключает повторное назначение.
- INDEX (`branch_group_id`, `rop_id`) обеспечивает поиск РОП группы.
- При физическом удалении РОП или группы соответствующие назначения удаляются через FK cascade. Для `assigned_by` — SET NULL.
- Филиал не дублируется: он определяется через группу. При назначении сервер проверяет совпадение филиала группы и РОП; FK сам по себе это условие не обеспечивает.
- Смена филиала, роли и назначения выполняется через сервис с транзакцией и блокировкой пользователя. Группу с участниками или данными нельзя переносить в другой филиал обычным редактированием.
- Снятие назначения удаляет строку; история хранится в отдельном журнале аудита.

Связи моделей: `User::supervisedGroups()` и `BranchGroup::rops()` через `belongsToMany`.

`users.branch_group_id` остаётся рабочей группой агента/МОП. Для роли РОП источником управленческого доступа служит только `rop_branch_groups`; собственное `branch_group_id` РОП не создаёт дополнительного доступа. Многогрупповое членство агентов и МОП в эту задачу не входит.

**4. Вычисление разрешённой области**

`allowedGroupIds` — группы из `rop_branch_groups`, принадлежащие текущему филиалу РОП. Для пользователя без филиала либо без назначений набор пуст.

Доступные сотрудники — пользователи с ролью `agent` или `mop`, у которых `branch_id` совпадает с филиалом РОП, а `branch_group_id` входит в `allowedGroupIds`. Неактивных сотрудников можно показывать отдельным фильтром для просмотра истории, но нельзя назначать ответственными.

Сам РОП видит собственный профиль через обычный механизм самообслуживания. Это не открывает записи вне его групп. Другие РОП, директор, администраторы и сотрудники других ролей не становятся управляемыми сотрудниками из-за совпадения группы.

Пустая область возвращает пустые списки и нулевые показатели. Записи без группы недоступны РОП. Запрещены автоматический переход к доступу по филиалу и исключения вида «создал запись — значит видит вне группы».

Настройки `contact_visibility_mode = branch`, общей видимости клиентов и collaborator-доступа не расширяют область РОП. Для других ролей сохраняется их действующая политика.

**5. Какая группа определяет доступ к данным**

Предлагается закреплять группу за бизнес-записью явно. Группа ответственного сотрудника определяет её при создании или контролируемой передаче, но не пересчитывается произвольно при каждом чтении. Это предотвращает незаметный перенос всей истории после изменения группы сотрудника.

| Данные | Источник групповой принадлежности |
|---|---|
| Агенты и МОП | Текущая `users.branch_group_id` |
| Объявления | `properties.branch_group_id` |
| Клиенты | `clients.branch_group_id` |
| Лиды и сделки | Добавить явную `branch_group_id` в соответствующие таблицы |
| Показы/бронирования | Добавить `bookings.branch_group_id`, заполнять по группе ответственного агента |
| Потребности клиента | Наследуют область клиента |
| Задачи, комментарии, документы, история изменений | Наследуют область своей основной карточки; самостоятельным задачам нужна собственная группа |
| Контрольные карточки объекта | Группа контролируемого объявления |
| Личные отчёты, KPI, посещаемость, геолокация | Группа сотрудника на дату события; сохранять снимок группы в записи/факте отчёта |
| Сводки, счётчики и выгрузки | Только доступные исходные записи |

Для корневых CRM-записей филиал должен совпадать с филиалом группы. Если таблица не имеет `branch_id`, филиал определяется через FK группы. Для объявлений с заполненным `branch_id` несоответствие группе считается ошибкой данных; отсутствие филиала нормализуется миграцией по группе, без угадывания при чтении.

Связь с доступной карточкой не открывает чужую карточку. Например, если показ группы A связан с объявлением группы C, РОП группы A видит разрешённые данные показа, но не внутреннюю карточку и контакты объявления C. Вложенные ресурсы проверяются отдельно; недоступные поля исключаются, а фронтенд показывает «Связанная запись недоступна». Телефоны и прочие скопированные приватные поля чужой карточки также не выдаются.

`created_by`, соавтор, участник продажи, collaborator и автор комментария не являются дополнительными источниками группового доступа. Исторический автор из другой группы не открывает его профиль целиком; допускается минимальная подпись автора, необходимая для истории доступной карточки.

Публичная витрина объявлений продолжает отдавать только публичную проекцию. Доступность опубликованного объявления гостю не означает доступ РОП к внутренним контактам, CRM, истории, финансовым полям или операциям этого объявления.

**6. Права на действия**

| Действие РОП | Требование |
|---|---|
| Списки и просмотр карточек | Только разрешённые группы |
| Создание записи | Явно выбранная разрешённая группа; при единственной группе можно заполнить автоматически |
| Редактирование, модерация, операции сделки | Группа разрешена и существующая политика разрешает конкретное действие |
| Назначение ответственного | Активный агент/МОП той же группы, что и запись; роль должна поддерживаться конкретным процессом |
| Передача записи между своими группами | Только специальная операция передачи с проверкой источника и назначения |
| Передача в чужую группу | Только администратор либо директор соответствующего филиала |
| Просмотр сотрудников и отчётности | Только доступные группы и разрешённые ролью поля/разделы |
| Изменение ролей, филиалов и состава групп | В этой версии РОП запрещено |
| Добавление/удаление собственных назначений | Запрещено |
| Создание и удаление групп | В этой версии РОП запрещено; каталог групп — только чтение своих групп |

Нельзя поменять `branch_group_id`, `branch_id`, `role_id` или `created_by` через произвольный PATCH и тем самым обойти правила. `created_by` при создании устанавливает сервер, при редактировании поле неизменно. РОП может создать запись от своего имени в выбранной разрешённой группе; авторство и ответственность разделены.

Глобальные справочники без персональных данных сохраняют действующий доступ. Модуль, для которого не определена групповая принадлежность, не должен выдавать РОП общие данные филиала: до адаптации его закрывают для РОП.

**7. Кто назначает РОП в группы**

- `superadmin` и `admin` управляют назначениями в пределах своих действующих полномочий.
- `branch_director` управляет назначениями только РОП своего филиала и только в группы своего филиала.
- РОП, МОП и агент не меняют назначения.

Несколько РОП одной группы имеют одинаковую область данных, но действующие ограничения действий и запрет самостоятельного согласования сохраняются. Отдельного «главного РОП» в этой версии нет.

При смене роли с `rop` назначения снимаются. При возвращении роли автоматически не восстанавливаются. При смене филиала прежние назначения снимаются в той же транзакции; группы нового филиала назначаются явно. На каждом чтении дополнительно проверяется актуальный филиал.

**8. Переводы сотрудников и данных**

Перевод агента/МОП не должен молча перемещать все его старые записи. Предлагаемый порядок:

1. Администратор или директор получает предварительный список активных записей сотрудника и выбирает: передать их в новую группу либо оставить в старой с новым ответственным.
2. Передача обновляет группу выбранных записей и зависимых сущностей, наследующих их область. Самостоятельные связанные клиенты и сделки требуют отдельного включения в передачу; одна ссылка не переносит их автоматически.
3. После операции у активной записи ответственный принадлежит её группе. Перевод сотрудника при неразрешённых конфликтах блокируется.
4. Закрытые сделки, завершённые показы и исторические отчёты сохраняют исходную группу. Старый РОП видит историю своей группы; новый не получает историю другой группы автоматически.
5. Операция фиксирует автора, старые/новые группы, ответственных и список переданных записей. При больших объёмах используется управляемая операция с блокировкой конфликтующих изменений; нельзя публиковать частично перенесённое состояние.

При снятии группы с РОП доступ прекращается со следующего запроса. Уже загруженные на устройство данные технически отозвать нельзя; интерфейс очищает локальный кэш после обновления области или отказа сервера.

Удаление группы с сотрудниками либо бизнес-данными запрещается до их явного переноса. Нельзя полагаться на существующие `nullOnDelete`, иначе данные потеряют область доступа.

**9. Backend и API**

Создать единый `RopGroupAccess` с методами получения разрешённых групп, ограничения запросов по группам, проверки карточки и проверки целевых сотрудников. SQL-фильтр применять до пагинации, `count`, агрегирования и экспорта. Использовать `EXISTS`/подзапрос либо JOIN с уникальностью результата; не загружать все идентификаторы записей в PHP.

Область должна одинаково работать в списках, карточках по ID, поиске по телефону, подборе объектов, autocomplete, дедупликации, пакетных операциях, вложенных ресурсах и скачивании файлов. Кандидаты-дубли из чужих групп не должны раскрывать контакты или существование приватной карточки.

Middleware проверяет входные фильтры, но не заменяет query scope и политики. Проверять все поля назначения независимо, включая вложенные массивы; нельзя выбирать между `agent_id` и `user_id`, пропуская другое переданное поле.

При изменении проверяются текущая запись и итоговое состояние после применения PATCH. В пакетной операции наличие недоступной записи отклоняет всю операцию без частичных изменений. Проверка и изменение выполняются транзакционно; операции передачи и назначения согласуют блокировки, чтобы отзыв доступа не обходился конкурентным запросом.

Предлагаемые новые маршруты, относительно существующего префикса API:

| Метод и маршрут | Контракт |
|---|---|
| `GET /users/{ropId}/supervised-groups` | Администратор/директор по своей области; РОП — только свои назначения |
| `PUT /users/{ropId}/supervised-groups` | Полная атомарная замена назначений, только уполномоченным руководителем |
| `GET /me/access-scope` | Актуальная область текущего пользователя для интерфейса |

Пример PUT: `{"branch_group_ids":[12,15],"version":7}`. Пустой массив снимает все назначения. Дубликаты, чужой филиал, отсутствующая группа и пользователь не с ролью РОП отклоняются. Сравнение `version` выполняется под блокировкой; несовпадение возвращает `409`. Версию области хранить в новом `users.access_scope_version` и увеличивать при изменении назначений, роли или филиала.

Пример ответа `/me/access-scope`: `{"scope_type":"groups","branch_id":3,"branch_group_ids":[12,15],"version":8}`. Это информация для UI, сервер никогда не доверяет её копии из запроса клиента.

Ошибки: недоступная/несуществующая карточка — одинаковый `404`; явно запрещённый фильтр группы/сотрудника — `403 RBAC_GROUP_SCOPE_VIOLATION` без чужих реквизитов; недопустимое действие — `403 FORBIDDEN_ACTION`; неверный формат — `422`; конфликт версии — `409`. Списки без фильтров возвращают только разрешённую область. Ответы об ошибках сохраняют стандартный формат проекта и `trace_id`.

В фоновых выгрузках права повторно проверяются при исполнении и скачивании. Готовая выгрузка привязывается к версии области; после её изменения требуется новая выгрузка. Уведомления и WebSocket-подписки фильтруются по актуальной области, отозванные подписки закрываются; уведомления со старыми приватными данными также не выдаются вне области. Приватные файлы скачиваются через авторизацию, без постоянной публичной ссылки.

Начальная реализация может вычислять группы на каждый запрос без межзапросного кэша. Если кэш вводится, ключ включает пользователя и версию области; изменение роли/филиала также инвалидирует его. Кэш содержимого карточек не заменяет проверку доступа при выдаче.

**10. Точки интеграции в проекте**

Разделить РОП и директора в `RbacBranchScope`, `EnforceRopBranchScope`, `ClientAccess`, `LeadAccess`, `DealAccess`, `DealPipelineAccess`, `BranchGroupController` и проверках пользователей. Директор сохраняет филиальную область.

Обновить выдачу и изменение объявлений в `PropertyController`, `PropertyModerationAccess`, `PropertyLiquidityAccess`, а также привязку клиентов в `ClientAttachService`. Проверять и модерационные решения, и формируемые `capabilities`; положительный capability не заменяет повторную серверную проверку действия.

Проверить KPI, планы РОП, дневные отчёты, посещаемость, геолокацию, уведомления и все маршруты с проверкой роли `rop`. Филиальные сводки нельзя отдавать целиком: показатели считаются по группам, а план, существующий только на уровне филиала и не имеющий обоснованного разбиения, РОП не показывается. Модуль сообщений сохраняет собственные правила участия: руководство группой само по себе не открывает чужую личную переписку.

Перед реализацией составить реестр маршрутов: ресурс → действие → источник группы → политика → тест. Этот список является обязательным артефактом реализации и закрывает формулировку «другие данные»; перечисленные выше файлы — стартовые точки, а не исчерпывающий аудит всех маршрутов.

Обновить описание роли `rop` в `config/roles.php` и каталоге ролей: «Руководитель отдела продаж с доступом к закреплённым группам своего филиала».

**11. Интерфейс**

В карточке РОП добавить множественный выбор «Закреплённые группы». Редактирование доступно администратору/директору по указанным правилам. В карточке группы показывать назначенных РОП.

У РОП фильтр групп содержит только разрешённые значения; «Все» означает все его группы. Фильтры сотрудников, назначения ответственных, списки и счётчики используют одну область. При создании и передаче записи выбор группы согласуется с ответственным.

При отсутствии назначений показывать: «Вам не назначены группы. Обратитесь к администратору или директору филиала». Смена назначений обновляет фильтры и данные; недоступная ранее открытая карточка закрывается при следующей проверке доступа.

**12. Миграция и выпуск**

1. Добавить таблицу назначений, версию области пользователя и недостающие поля групп у корневых сущностей/исторических фактов. Проверить индексы по реальным запросам; базово нужны индексы группы и используемых комбинаций филиала, группы, статуса/даты.
2. Подготовить отчёт: РОП и их группы, записи без группы, несоответствия группы ответственному, межфилиальные конфликты, связи карточек разных групп.
3. Для пустой группы записи использовать группу основного ответственного в том же филиале; при его отсутствии — однозначную группу родительской карточки, затем создателя. Существующую непустую группу не перезаписывать автоматически. Конфликты вынести на ручное исправление.
4. Исторические отчёты восстанавливать по достоверной истории групп. Если её нет, не приписывать прошлые события текущей группе сотрудника: оставить без группового доступа до классификации.
5. Назначения РОП загрузить из явной таблицы соответствий, проверенной администратором. `users.branch_group_id` РОП можно предложить как кандидата, но нельзя автоматически назначать ему весь филиал.
6. До включения ограничения проверить, что рабочие РОП получили назначения, а активные записи распределены или явно помещены в очередь разбора, доступную администратору/директору.
7. Выпустить backend и совместимый интерфейс, затем включить групповую политику. Неразобранные записи остаются закрытыми для РОП.

Журналировать изменения назначений и групп записей: исполнитель, причина, время, состояние до/после, идентификатор запроса/операции. Если подходящего журнала нет, создать отдельный `group_access_audit_logs` с этими полями; удаление pivot-строки не должно удалять аудит.

При проблеме выпуска не возвращать РОП широкий доступ по филиалу. Допустимый аварийный режим — временно закрыть затронутый модуль для РОП и сохранить назначения/группы. Обратная миграция не должна уничтожать новую классификацию данных.

**13. Критерии приёмки**

1. РОП групп A/B видит агентов, МОП и данные A/B; данные C того же филиала и данные другого филиала отсутствуют.
2. Два РОП общей группы видят её данные без дублирования строк и завышения сумм.
3. Прямой ID, телефон, экспорт, поиск, вложенный файл и WebSocket не обходят ограничение.
4. Добавление группы открывает доступ со следующего запроса; снятие закрывает, включая фоновые выгрузки и новые скачивания.
5. Без групп/филиала, при `branch_group_id = null` и при межфилиальном несоответствии доступ закрыт.
6. Собственное авторство, соавторство, collaborator и режим видимости контактов `branch` не открывают чужую группу РОП.
7. РОП не назначает себя в группу и не переносит сотрудников/записи в чужую область через PATCH или массовую операцию.
8. Перевод сотрудника обрабатывает активные записи явно, сохраняя историю прежней группы и отсутствие частично видимого переноса.
9. Изменение роли/филиала снимает прежние назначения; конкурентные обновления не возвращают отозванный доступ.
10. Доступная карточка не раскрывает контакты и приватные вложения связанной чужой карточки.
11. Счётчики, KPI и выгрузки совпадают с той же групповой выборкой; исторические факты не переписываются при переводе агента.
12. Директор, администраторы, МОП, агенты и публичная витрина сохраняют свои действующие правила; новые права на действия не появляются.
13. На репрезентативном объёме данных проверены SQL-планы, пагинация и отсутствие N+1; групповой фильтр выполняется в БД.

Результат реализации: миграции и подготовка данных, единый серверный механизм области РОП, API назначений, интерфейс, аудит, реестр покрытых маршрутов и автоматические позитивные/негативные проверки. Настоящее ТЗ фиксирует предлагаемую логику; изменения доступа в рабочем приложении этим документом не выполняются.
