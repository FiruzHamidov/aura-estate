# ТЗ: оценка ликвидности квартир

## 1. Назначение

Разработать на платформе модуль, который для каждой квартиры, выставленной на продажу, рассчитывает:

- индекс ликвидности от 0 до 100;
- позицию цены: «ниже рынка», «в рынке» или «выше рынка»;
- категорию ликвидности;
- ориентировочный срок продажи;
- уровень достоверности оценки;
- расшифровку факторов и рекомендации по улучшению позиции объекта.

Главный пользовательский результат — автоматически выделить квартиры, которые выгодно выглядят относительно аналогов своего района, и сформировать из них ролевые списки:

- маркетологу — что сейчас продвигать в социальных сетях;
- РОП и руководящим ролям — какие ликвидные объекты есть в портфеле филиала и у каждого агента;
- агенту — какие из его квартир наиболее ликвидны и какие стоит в первую очередь предлагать клиентам.

Под ликвидностью понимается вероятность продать квартиру в разумный для ее сегмента срок без существенного дополнительного снижения цены. Оценка должна быть относительной: квартира сравнивается прежде всего с похожими квартирами в том же районе, а не со всем городом.

Модуль предназначен для агентов, руководителей отдела продаж, маркетологов и администраторов. Внутренний балл публичному покупателю не показывается; при достаточной достоверности ему может отображаться только положительный бейдж выгодной цены.

## 2. Бизнес-цели

- помочь агенту объяснить собственнику, насколько цена соответствует рынку;
- выделять объекты, которые вероятнее продадутся быстрее;
- автоматически формировать очередь объектов для продвижения в социальных сетях;
- дать агенту рейтинг собственных ликвидных квартир;
- дать РОПу рейтинг ликвидных квартир филиала с разбивкой по агентам;
- заранее находить переоцененные и зависшие объявления;
- учитывать реальный спрос клиентов по каждому району;
- дать РОПу отчет по качеству портфеля и динамике ликвидности;
- накапливать данные для последующего перехода от правил к статистической модели.

## 3. Область первой версии

В MVP рассчитывать ликвидность только для квартир с `offer_type = sale`. Аренда, дома, земля и коммерческие объекты должны быть исключены: для них позднее потребуются отдельные модели и веса.

Оценка не является гарантией продажи или официальной оценкой стоимости. В интерфейсе необходимо использовать формулировку «оценка на основе данных платформы».

## 4. Термины

- **Дата выхода на рынок** — дата первой публикации одобренного объявления (`listed_at`), а не `created_at`.
- **DOM (days on market)** — число активных дней от `listed_at` до `sold_at`; периоды снятия с публикации не учитываются.
- **Эффективная цена** — `discount_price`, если она задана и больше нуля, иначе `price`.
- **Цена за м²** — эффективная цена / `total_area`. В MVP сравниваются только объекты с одинаковой валютой.
- **Когорта аналогов** — набор сопоставимых объектов, используемый для расчета рыночных показателей.
- **Активное предложение** — опубликованный объект, не закрытый и не проданный.
- **Успешное закрытие** — объект со статусом `sold` и заполненным `sold_at`. `sold_by_owner` учитывать отдельно и не смешивать с подтвержденными продажами до проверки качества данных.

## 5. Нормализация района — обязательное условие

Сейчас район хранится строкой в `properties.district`, `locations.district` и `client_needs.district`. Это допускает варианты написания и искажает статистику.

Необходимо создать справочник районов:

### `districts`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | Идентификатор |
| `location_id` | FK | Город/локация |
| `name` | string | Отображаемое название |
| `slug` | string | Нормализованный ключ |
| `aliases` | json nullable | Альтернативные написания |
| `is_active` | boolean | Активность |

Добавить `district_id` в `properties`, `client_needs` и при необходимости `new_buildings`. Старое строковое поле временно сохранить для обратной совместимости. При сохранении объекта API должен сопоставлять строку со справочником либо требовать `district_id`. Неизвестный район не создавать автоматически без модерации.

Если имеются координаты, проверить, что объект попадает в границы выбранного района. Полигон района можно добавить во второй версии.

## 6. Формирование аналогов

Для объекта формируется когорта в следующем порядке:

1. тот же город и район;
2. продажа;
3. тот же тип недвижимости — квартира;
4. первичный и вторичный рынок не смешиваются (`is_from_developer` или отдельный признак рынка);
5. такое же число комнат; студии являются отдельным сегментом;
6. площадь в диапазоне ±20%;
7. данные за последние 12 месяцев для продаж и текущие активные объявления.

Если подтвержденных продаж меньше 15, расширять когорту последовательно:

1. площадь ±30%;
2. соседнее число комнат, но с меньшим весом;
3. тот же сегмент по всему городу.

Расширение когорты всегда снижает уровень достоверности. Пока источник валютного курса не утвержден, квартиры в разных валютах находятся в разных когортах. После подключения источника допускается пересчет только по курсу, сохраненному на дату снимка. Нельзя сравнивать исходные USD и TJS напрямую.

Выбросы по цене за м² исключаются методом IQR либо отсечением ниже 1-го и выше 99-го перцентиля при достаточном объеме данных. Объявления с нулевой ценой, ценой «по запросу» или отсутствующей площадью не участвуют в ценовых расчетах.

## 7. Итоговая формула MVP

```text
liquidity_score =
    0.25 × district_market_score +
    0.45 × price_score +
    0.15 × demand_score +
    0.15 × apartment_fit_score
```

Цена относительно рынка района является главным фактором MVP. Каждый компонент принимает значение от 0 до 100. Итог округляется до целого. Веса должны храниться в конфигурации и изменяться без релиза приложения. При отсутствии компонента его вес пропорционально распределяется между доступными компонентами, но итоговая достоверность снижается. Не подставлять ноль за отсутствующие данные.

Просмотры, избранное и подборки не входят в основной балл ликвидности. Они отображаются как отдельное подтверждение интереса. Это исключает замкнутый цикл, при котором уже продвигаемый объект получает просмотры и только из-за рекламы начинает считаться более ликвидным.

### 7.1. Рынок района — 25%

Компонент отражает фактическую скорость и долю продаж сопоставимых квартир в районе:

```text
district_market_score =
    0.60 × dom_percentile_score +
    0.40 × sell_through_percentile_score
```

- `dom_percentile_score` выше у районов с меньшим медианным DOM;
- `sell_through_rate = sold_count / (sold_count + active_count)` за окно 12 месяцев;
- показатели района сравниваются с аналогичными сегментами остальных районов того же города;
- использовать медиану, а не среднее значение;
- при малой выборке показатель района сглаживается в сторону городского значения (empirical Bayes / weighted average).

Пример сглаживания:

```text
adjusted_metric = (n / (n + 30)) × district_metric
                + (30 / (n + 30)) × city_metric
```

Это не позволяет району с двумя быстрыми продажами необоснованно получить максимальную оценку.

### 7.2. Конкурентность цены — 45%

Сначала вычислить отклонение цены за м² объекта от медианы активных и недавно проданных аналогов:

```text
price_delta_pct = (object_price_per_sqm / cohort_median_price_per_sqm - 1) × 100
```

Базовая шкала:

| Отклонение от медианы | Балл |
|---|---:|
| ниже на 10% и более | 100 |
| от −10% до 0% | линейно 100 → 85 |
| от 0% до +5% | линейно 85 → 70 |
| от +5% до +10% | линейно 70 → 50 |
| от +10% до +20% | линейно 50 → 20 |
| выше на 20% | 0–20 |

Сильно заниженная цена повышает ликвидность, но одновременно должна создавать отдельный предупреждающий флаг `price_anomaly_low`; это защита от ошибочного ввода и не должно автоматически трактоваться как рекомендация снизить цену.

В расчетах показывать две медианы: по активным предложениям и по фактическим продажам. Если `actual_sale_price` заполнена недостаточно часто, основой MVP может быть медиана эффективной цены объявления, но интерфейс должен явно подписывать источник.

Одновременно рассчитывать понятную позицию цены:

| Отклонение цены за м² | Метка |
|---:|---|
| не выше −5% | `below_market` — «Цена ниже рынка» |
| от −5% до +5% | `at_market` — «Цена в рынке» |
| выше +5% | `above_market` — «Цена выше рынка» |

Порог должен храниться в конфигурации. Метка «Ликвидная — цена ниже рынка» показывается, если `price_position = below_market`, общий `liquidity_score >= 65` и достоверность не ниже `medium`.

### 7.3. Реальный спрос — 15%

Использовать активные потребности покупателей из `client_needs` типа `buy` и `invest`:

- совпадает город и район;
- бюджет включает цену объекта с допуском ±10%;
- совпадает тип недвижимости;
- комнаты и площадь попадают в диапазон потребности;
- потребность не закрыта и обновлялась не более 90 дней назад.

```text
demand_supply_ratio = weighted_matching_needs / active_comparable_supply
```

Одна потребность одного клиента считается один раз. Свежая потребность получает больший вес: до 30 дней — 1.0, 31–60 — 0.7, 61–90 — 0.4. Значение преобразуется в балл по перцентилю среди объектов того же города. Дополнительно API возвращает `matching_active_needs_count`, доступный только сотрудникам с соответствующим правом.

### 7.4. Соответствие востребованному формату — 15%

Оценить характеристики квартиры относительно квартир, которые действительно продавались в данном районе:

- комнаты — 30% компонента;
- диапазон общей площади — 20%;
- этаж — 20%;
- состояние/ремонт — 15%;
- парковка, ипотека и другие подтвержденные удобства — 15%.

Для этажа в MVP применить понятные правила:

- средние этажи — без штрафа;
- первый этаж — штраф, размер которого определяется статистикой района, по умолчанию 10 баллов компонента;
- последний этаж — по умолчанию 7 баллов;
- этаж выше 5-го без подтвержденного лифта — 15 баллов;
- некорректный этаж (`floor > total_floors`) блокирует расчет и создает ошибку качества данных.

Фиксированные штрафы являются стартовыми. После накопления не менее 50 подтвержденных продаж в сегменте их необходимо заменить фактическим влиянием характеристик на DOM.

### 7.5. Интерес к объявлению — отдельный показатель

Показатель рассчитывается только после 7 полных дней публикации. До этого ставится признак `insufficient_exposure`; на основной балл ликвидности это не влияет.

Сигналы:

- уникальные просмотры в день — 40%;
- добавления в избранное / уникальные просмотры — 25%;
- попадания в отправленные клиентам подборки — 25%;
- обращения или назначенные показы — 10%, когда такие события доступны.

Все показатели сравниваются с аналогами того же района и возраста объявления.

На платформе уже есть `properties.views_count` и endpoint `trackView`: один просмотр объекта с одинаковым IP + User-Agent засчитывается не чаще одного раза в день. Поэтому в MVP этот счетчик является основным источником сигнала просмотров:

```text
views_velocity = views_count / active_days_since_listed_at
```

Само абсолютное число просмотров не оценивается: 100 просмотров за 5 дней и за 100 дней должны давать разные баллы. `views_velocity` переводится в балл по перцентилю среди аналогов того же района, сегмента и возраста объявления.

Для запуска MVP новый детальный журнал просмотров не является блокирующим. Однако `views_count` не позволяет восстановить динамику по дням, надежно исключить сотрудников и корректно обработать периоды паузы. Поэтому необходимо сохранять ежедневные агрегаты просмотров; детальный журнал событий остается требованием следующего этапа.

## 8. Категории результата

| Балл | Категория | Интерпретация |
|---:|---|---|
| 80–100 | Очень высокая | Один из наиболее конкурентных объектов сегмента |
| 65–79 | Высокая | Вероятна продажа быстрее медианы сегмента |
| 45–64 | Средняя | Соответствует типичному предложению рынка |
| 25–44 | Низкая | Есть существенные факторы, замедляющие продажу |
| 0–24 | Очень низкая | Высокий риск длительной экспозиции |

Категория должна выводиться вместе с достоверностью. Нельзя показывать пользователю только цвет или только итоговый балл без объяснения факторов.

## 9. Приоритет продвижения в социальных сетях

Ликвидность и приоритет продвижения — разные показатели. Ликвидность отвечает на вопрос «насколько объект конкурентен рынку», а `promotion_priority_score` — «что маркетологу публиковать следующим».

### 9.1. Условия попадания в список маркетолога

Объект попадает в очередь «Рекомендуем продвигать», если одновременно:

- это активная одобренная квартира на продажу;
- `liquidity_score >= 65`;
- цена не выше медианы аналогов (`price_position` равна `below_market` или `at_market`);
- достоверность не ниже `medium`;
- есть обложка и не менее 5 качественных фотографий;
- заполнены район, цена, площадь, комнаты, этаж и описание;
- объект не имеет ошибок данных, запрета собственника или юридического ограничения публикации;
- объект не публиковался в том же канале в течение настраиваемого периода, по умолчанию 14 дней.

Если объект ликвидный, но медиа не готовы, он попадает в отдельную очередь «Подготовить контент», а не исчезает из списка.

### 9.2. Формула приоритета

```text
promotion_priority_score =
    0.60 × liquidity_score +
    0.15 × content_readiness_score +
    0.10 × listing_freshness_score +
    0.10 × rotation_score +
    0.05 × marketing_opportunity_score
```

- `content_readiness_score` — качество и полнота фото, видео, описания и планировки;
- `listing_freshness_score` — актуальность объявления и подтвержденная доступность;
- `rotation_score` — выше, если объект давно не продвигался; не позволяет постоянно показывать одни квартиры;
- `marketing_opportunity_score` — выше у ликвидного объекта с пока еще низким органическим охватом.

Маркетолог может сортировать очередь по приоритету, району, комнатам, цене, агенту и дате последнего продвижения. Ручное закрепление допустимо, но причина и пользователь должны записываться в аудит.

### 9.3. Жизненный цикл продвижения

Для объекта маркетолог может установить:

- `recommended` — рекомендован системой;
- `content_needed` — нужно подготовить контент;
- `planned` — запланирован;
- `published` — опубликован;
- `skipped` — пропущен с обязательной причиной;
- `expired` — объект уже неактуален.

Для публикации сохраняются канал (`instagram`, `facebook`, `telegram`, другое), ссылка, маркетолог, дата публикации и при наличии показатели результата. Проданный или снятый объект автоматически удаляется из активной очереди.

## 10. Прогноз срока продажи

В MVP прогноз строится от медианного DOM когорты:

```text
predicted_days = cohort_median_dom
               × price_multiplier
               × demand_multiplier
               × apartment_multiplier
```

Множители вычисляются из соответствующих баллов и ограничиваются диапазоном 0.5–2.0. Результат показывается диапазоном, а не точной датой, например «45–70 дней».

Если подтвержденных продаж меньше 15, вместо срока показывать «Недостаточно данных», даже если предварительный индекс рассчитан. После накопления истории прогноз необходимо откалибровать по фактической доле продаж за 30, 60 и 90 дней.

## 11. Достоверность

Рассчитывать `confidence_score` от 0 до 100 отдельно от ликвидности.

Факторы достоверности:

- число подтвержденных продаж в когорте;
- число активных аналогов;
- доля заполненных обязательных характеристик;
- наличие нормализованного района;
- возраст и актуальность данных;
- наличие истории цены и статусов;
- достаточная экспозиция для поведенческих данных.

Уровни:

- `high`: 75–100, не менее 50 продаж в строгой или близкой когорте;
- `medium`: 45–74, не менее 15 продаж;
- `low`: 0–44 или использован городской fallback.

Низкая достоверность не должна автоматически означать низкую ликвидность.

## 12. Требования к данным и хранению

### 12.1. Новые поля `properties`

- `district_id` nullable FK;
- `listed_at` nullable timestamp;
- `liquidity_score` nullable unsigned tinyint — последний расчет;
- `liquidity_category` nullable string;
- `liquidity_confidence` nullable unsigned tinyint;
- `liquidity_calculated_at` nullable timestamp;
- `liquidity_model_version` nullable string.
- `price_position` nullable string — `below_market`, `at_market`, `above_market`;
- `price_delta_pct` nullable decimal;
- `promotion_priority_score` nullable unsigned tinyint;
- `promotion_eligibility` nullable string — `eligible`, `content_needed`, `not_eligible`.

Поля на объекте используются для быстрой фильтрации. Полная расшифровка хранится в снимках.

### 12.2. `property_liquidity_snapshots`

- `id`, `property_id`;
- `score`, `category`, `confidence_score`, `confidence_level`;
- `predicted_days_from`, `predicted_days_to`;
- четыре компонентных балла и отдельные показатели интереса;
- `cohort_definition` JSON;
- `cohort_sold_count`, `cohort_active_count`, `cohort_median_dom`, `cohort_median_price_sqm`;
- `factors` JSON — положительные и отрицательные причины;
- `recommendations` JSON;
- `model_version`, `calculated_at`;
- timestamps.

Индекс: `(property_id, calculated_at)`. Снимки нужны для графика динамики и аудита изменения оценки.

### 12.3. `district_market_metrics`

Ежедневный агрегат по дате, городу, району, типу рынка, комнатам и при необходимости ценовому сегменту. Хранить число активных объектов, число продаж, медианный DOM, медианную цену за м², sell-through rate и размер выборки.

### 12.4. История событий

Добавить либо унифицировать таблицы:

- `property_status_history` — публикация, пауза, снятие, продажа;
- `property_price_history` — цена, валюта, курс и дата изменения;
- `property_view_daily_stats` — дата, `property_id`, накопительный `views_count`, прирост за день и число активных дней;
- `property_events` — `favorite`, `selection_sent`, `lead`, `showing` с `property_id`, временем и обезличенным actor/session key; событие `view` можно добавить во второй версии при необходимости более точной аналитики.

Текущая дедупликация просмотра по IP + User-Agent + календарному дню сохраняется. В следующей версии просмотры владельца, назначенного агента, администраторов и ботов должны исключаться из пользовательского интереса. Не хранить исходные IP и User-Agent в аналитических таблицах.

Повторная публикация того же объекта не должна обнулять DOM. Для объединения дублей использовать стабильный `object_key`, собственника, адрес, координаты и характеристики. Ручное объединение должно быть доступно администратору.

### 12.5. `property_social_promotions`

- `property_id`, `channel`, `status`;
- `priority_score_snapshot`, `liquidity_score_snapshot`;
- `planned_at`, `published_at`, `published_url`;
- `assigned_to`, `published_by`;
- `skip_reason`, `notes`;
- `metrics` JSON — охват, переходы, обращения при наличии интеграции;
- timestamps.

Индексировать `(status, channel, planned_at)` и `(property_id, channel, published_at)`.

## 13. Пересчет

- районные агрегаты: ежедневно ночью;
- все активные квартиры: ежедневно после обновления агрегатов;
- конкретный объект: асинхронно после изменения цены, района, площади, комнат, статуса или ключевых характеристик;
- после новой продажи: пересчитать затронутый сегмент района;
- ручной пересчет: только для администратора, с rate limit;
- каждый расчет сохраняет `model_version`, чтобы результат можно было воспроизвести.

Расчет выполняется очередью и не должен замедлять сохранение объявления.

- гостю и роли `client` при `price_position = above_market` не возвращать ни позицию цены, ни косвенный флаг, по которому ее можно восстановить;
- гостю и роли `client` при `price_position = below_market` возвращать только публичный объект `public_price_badge` с кодом, названием и текстом объяснения;
- внутренние поля ликвидности не должны сначала попадать в общий JSON с последующей попыткой скрыть их только на фронтенде.

## 15. Ролевой доступ и интерфейс

### 15.1. Агент (`agent`)

- видит раздел «Мои ликвидные квартиры»;
- видит только объекты, назначенные ему или созданные им в рамках действующих правил доступа;
- сортировка по ликвидности, позиции цены, просмотрам и дате обновления;
- первый блок — «Ликвидные: цена ниже рынка»;
- второй блок — «Цена в рынке»;
- третий блок — «Нужно улучшить», с причинами;
- может открыть объяснение и предложить объект клиенту;
- не может менять балл или приоритет вручную.

### 15.2. РОП и роли выше (`rop`, `mop`, `branch_director`, `admin`, `superadmin`)

- видят ликвидные квартиры в пределах разрешенного филиала/группы или всей компании;
- видят группировку по агентам и районам;
- могут определить, у какого агента есть объекты для быстрой продажи;
- видят объекты, рекомендованные маркетологу, и статус продвижения;
- могут поставить бизнес-приоритет с обязательным комментарием, не изменяя расчетную ликвидность;
- получают отчет: количество ликвидных объектов, доля цены ниже рынка, зависшие объекты и результаты продвижения.

### 15.3. Маркетолог (`marketing`) и менеджер рилсов (`reels_manager`)

- видят общую очередь «Что продвигать» в разрешенном организационном контуре;
- по умолчанию список отсортирован по `promotion_priority_score`;
- видят причину рекомендации: например «цена на 8% ниже рынка района, высокий спрос на 2-комнатные»;
- видят готовность контента и дату последнего продвижения;
- могут планировать, отмечать публикацию, прикреплять ссылку или пропускать с причиной;
- не видят персональные данные собственника и покупателей без отдельного права.

### 15.4. Внешний агент, клиент и публичный пользователь

В MVP не видят внутренний балл, маркетинговый приоритет, аналоги и активные потребности клиентов.

Для неавторизованного пользователя и пользователя с ролью `client` действуют отдельные правила отображения цены относительно рынка:

- `above_market` — не возвращать в публичном API и не показывать метку «Цена выше рынка»;
- `at_market` — метку можно не показывать, чтобы не перегружать карточку;
- `below_market` — разрешено показать положительный бейдж «Выгодная цена» или «Цена ниже рынка» при достаточной достоверности;
- не показывать публично точный `price_delta_pct`, медианную цену аналогов, внутренние причины, score и рекомендации агенту;
- отсутствие публичной метки не должно позволять определить, что внутренний статус объекта равен `above_market`.

Внутренние роли `agent`, `rop`, `mop`, `branch_director`, `marketing`, `reels_manager`, `admin` и `superadmin` видят все три позиции цены в пределах своего scope доступа.

### Карточка объекта в CRM

Показать:

- бейдж «Ликвидность: 72/100 — высокая»;
- главный бейдж «Цена ниже рынка на 4,2%»;
- достоверность «средняя»;
- прогноз «ориентировочно 42–65 дней»;
- дату последнего расчета;
- действие «Почему такая оценка?».

### Бейдж и объяснение

Каждый отображаемый бейдж ликвидности или выгодной цены должен иметь объяснение:

- на desktop при наведении показывается короткий tooltip;
- при клике открывается подробный popover или модальное окно;
- на мобильном устройстве объяснение открывается по тапу, так как hover отсутствует;
- бейдж доступен с клавиатуры, имеет видимый focus-state и `aria-label`;
- текст и иконка используются вместе с цветом — смысл нельзя передавать только цветом.

Короткий tooltip для публичного бейджа:

> Цена за м² ниже, чем у похожих квартир в этом районе.

Подробное объяснение для гостя или клиента:

> Платформа сравнила цену за квадратный метр с похожими активными квартирами в том же районе: учитывались тип объекта, количество комнат и площадь. Это информационная оценка на основе доступных объявлений, а не гарантия продажи или официальная оценка стоимости.

Подробное объяснение для внутренней роли дополнительно показывает:

- отклонение цены за м² от медианы в процентах;
- район и параметры использованной когорты;
- количество аналогов;
- дату расчета и уровень достоверности;
- основные факторы ликвидности;
- ссылку «Как рассчитывается ликвидность».

Если `confidence = low`, публичный положительный бейдж не показывается. Внутреннему пользователю он показывается с предупреждением «Недостаточно данных».

### Детальная расшифровка

- четыре компонентных балла и отдельный показатель пользовательского интереса;
- сравнение цены за м² с медианой района;
- медианный срок продажи аналогов;
- число аналогов;
- 3 главных положительных и 3 главных отрицательных фактора;
- практические рекомендации;
- график изменения ликвидности и цены.

### Отчет РОПа

- распределение портфеля по пяти категориям;
- доля объектов с низкой достоверностью;
- зависшие объекты: более 60/90 дней и score ниже 45;
- объекты, у которых балл снизился более чем на 10 за 30 дней;
- фильтры по району, агенту, филиалу, комнатам и цене;
- экспорт с датой и версией расчета.

### Рабочий экран маркетолога

- вкладки «Рекомендуем», «Нужен контент», «Запланировано», «Опубликовано», «Пропущено»;
- карточка: фото, цена, цена за м², отклонение от рынка, район, агент, ликвидность, просмотры в день, готовность контента;
- быстрые действия «Запланировать», «Опубликовано», «Пропустить»;
- защита от повторного продвижения одного объекта в одном канале ранее заданного срока;
- фильтры по району, агенту, комнатам, диапазону цены, каналу и наличию видео.

Цветовая индикация должна сопровождаться текстом и числом. Нельзя использовать только красный/зеленый цвет.

## 16. Автоматические рекомендации

Рекомендации генерируются только из известных причин, а не свободным текстом ИИ:

- цена выше медианы: показать цену, при которой объект попадет как минимум в категорию `high`, но не называть ее гарантированной ценой продажи;
- мало просмотров при нормальной цене: проверить фото, заголовок и полноту карточки;
- высокий спрос, но мало подборок: предложить агенту отправить объект подходящим клиентам;
- низкая полнота данных: перечислить конкретные незаполненные поля;
- длительная экспозиция без изменения цены: предложить пересмотр стратегии;
- район или координаты не подтверждены: запросить исправление данных.

## 17. Контроль качества и защита от искажений

- не считать создание объявления продажей;
- не использовать `updated_at` как дату повторного выхода на рынок;
- исключать тестовые, удаленные, отклоненные и дублирующиеся записи;
- отдельно считать подтвержденные продажи и `sold_by_owner`;
- сохранять валютный курс, использованный в каждом снимке;
- не позволять повторной публикацией искусственно уменьшать DOM;
- логировать ручное изменение района, даты публикации, продажи и фактической цены;
- при цене, площади или этаже вне допустимых границ возвращать состояние `data_error`, а не вводящий в заблуждение балл;
- при отсутствии обязательных данных возвращать `not_calculated` со списком причин.

Обязательные данные для ценовой оценки: город, нормализованный район, тип объекта, рынок, цена, валюта, площадь и комнаты.

## 18. Метрики эффективности модуля

Через 3 месяца после запуска измерить:

- долю проданных за 30/60/90 дней в каждой категории;
- медианный фактический DOM по категориям — он должен монотонно расти от высокой ликвидности к низкой;
- ошибку диапазона прогнозируемого срока;
- долю объектов, попавших в заявленный диапазон;
- влияние изменения рекомендованной цены на просмотры, подборки и продажу;
- долю объектов без расчета и причины отсутствия оценки;
- точность района и полноту ключевых данных.
- сколько рекомендованных объектов маркетолог опубликовал;
- обращения и продажи после продвижения;
- долю ротации — система не должна рекомендовать только один и тот же небольшой набор квартир.

Целевой критерий после калибровки: не менее 70% объектов категории «очень высокая» продаются быстрее медианного DOM своего сегмента, а фактический DOM категорий не пересекается хаотично.

## 19. Этапы реализации

### Этап 0. Аудит данных

- проверить заполненность `district`, `sold_at`, `actual_sale_price`, площади и комнат;
- определить долю подтвержденных продаж и дублей;
- построить распределение DOM и цены за м² по районам;
- не утверждать постоянные веса, пока не известен объем данных.

### Этап 1. Подготовка данных

- справочник районов и миграция `district_id`;
- `listed_at`, история статусов и цены;
- журнал уникальных событий;
- ежедневные районные агрегаты.

### Этап 2. MVP

- rule-based формула версии `liquidity-rules-v1`;
- фоновые расчеты и снимки;
- API карточки, фильтры и внутренняя расшифровка;
- экран агента «Мои ликвидные квартиры»;
- очередь маркетолога «Что продвигать» и история публикаций;
- отчет РОПа с группировкой по агентам.

### Этап 3. Калибровка

- сравнить прогноз с фактическими продажами;
- откалибровать шкалы и веса отдельно по городу и сегменту;
- добавить вероятность продажи за 30/60/90 дней;
- провести A/B-проверку рекомендаций агентам.

### Этап 4. Статистическая модель

После накопления достаточной истории заменить часть ручных правил survival-моделью или gradient boosting с прогнозом `P(sale ≤ N days)`. Rule-based расшифровку сохранить как слой объяснения. Обучение и проверку разделять по времени, чтобы будущие данные не попадали в прошлые прогнозы.

## 20. Критерии приемки MVP

1. Для активной квартиры с полными данными API возвращает балл, категорию, достоверность, компоненты, аналоги и причины.
2. Аналоги сначала выбираются внутри района; городской fallback явно отражается в ответе и снижает confidence.
3. Изменение эффективной цены запускает новый расчет и сохраняет предыдущий снимок.
4. Проданный объект учитывается в DOM только при корректных `listed_at` и `sold_at`.
5. Паузы публикации исключаются из DOM, повторная публикация не обнуляет срок.
6. Объекты с разными валютами не сравниваются напрямую; до подключения утвержденного источника курса они находятся в разных когортах.
7. При выборке менее 15 продаж срок продажи не показывается как достоверный.
8. До 7 дней публикации engagement имеет нейтральное значение и признак недостаточной экспозиции.
9. Некорректные или отсутствующие обязательные данные дают `not_calculated`/`data_error` с причинами.
10. Ни один API ликвидности не раскрывает персональные данные клиентов.
11. Пересчет выполняется очередью и не увеличивает заметно время сохранения объекта.
12. Все результаты содержат время расчета и версию модели.
13. Квартира с ценой за м² не менее чем на 5% ниже медианы района, баллом от 65 и confidence не ниже medium получает видимую метку «Ликвидная — цена ниже рынка».
14. Агент видит рейтинг только доступных ему квартир; РОП — разрешенного филиала; руководящие роли — согласно существующему scope доступа.
15. Маркетолог получает отдельную очередь готовых к продвижению объектов, а не просто сортировку по просмотрам.
16. Недавно продвинутый объект понижается в очереди или исключается на период ротации.
17. Ручной бизнес-приоритет не изменяет расчетный `liquidity_score` и сохраняется в аудите.
18. Проданный, снятый или отклоненный объект автоматически исчезает из активных ролевых списков.
19. Гость и пользователь с ролью `client` не получают и не видят метку `above_market`, точное отклонение от рынка или внутренний балл.
20. Скрытие `above_market` реализовано на backend-сериализации и покрыто feature-тестами, а не только условием на frontend.
21. Публичный положительный бейдж показывается только при достоверности не ниже `medium`.
22. На desktop у бейджа есть tooltip по наведению, по клику открывается подробное объяснение; на мобильном объяснение открывается по тапу.
23. Бейдж доступен с клавиатуры и имеет текстовое описание для screen reader.

## 21. Открытые вопросы перед разработкой

- Как надежно отделить первичный рынок от вторичного для старых объектов?
- Насколько полно и корректно агенты заполняют `sold_at` и `actual_sale_price`?
- Есть ли дата фактической первой публикации в исторических данных?
- Можно ли считать `sold_by_owner` подтвержденной продажей?
- Какие районы и альтернативные написания должны войти в справочник?
- Есть ли на платформе события обращения и показа, которые можно связать с объектом?
- Какой источник валютного курса утвержден бизнесом?
- Кто из ролей имеет право видеть совпадающие активные потребности покупателей?

Без ответов на эти вопросы MVP можно реализовать технически, но точность оценки и прогноза срока должна маркироваться как предварительная.
